冷启动：工作分类与依赖关系

Wan 2.1、MiniMax H3 和 LTX 2.5 在当前代码中如何完成 cold start：三类工作、权重从文件到 GPU 的路径、框架 API 管什么，以及每个模型声明的依赖。本页描述的是声明，不是实测耗时；真实容器时间线见 startup profile。

模型准备

准备 native owner、CUDA 状态、模型对象和工作 buffer。

目的是让 owner 能够执行模型计算。

权重准备

读取训练参数，并把它们放到 GPU 内存。

它回答：参数字节在哪里，计算是否已经能用？

请求准备

为一次请求准备输入、编码结果和 layout。

它回答：这次请求需要哪些输入、conditioning 和张量尺寸？

这三类工作不是三套 API。一个声明的 callback 里可能同时有多类工作。Wan 的 request-backend 先跑 CPU 前端，等 context 就绪后再恢复 attention plan；H3 每个组件的原生 load 在同一个 callback 里创建 context、启动 reader 并上传。执行器调度的是 callback，所以只有拆成不同 callback 的工作才能重叠。

2. 权重从文件到 GPU 的路径

CPU reader 可以在 CUDA 就绪之前开始读文件；H2D 拷贝要等 CUDA context 和已填好的 buffer。

CPU 内存

CUDA 就绪之前，reader 就可以填 buffer；这时 buffer 还没有向 CUDA 注册。

Buffer 来自有上限的池，整个 checkpoint 从不会整体放进 pinned memory。

GPU 内存

CUDA 就绪后，已填好的 buffer 注册并拷贝；后面的读取和前面的拷贝重叠。

拷贝调用返回不代表字节已经到位；loader 等每个拷贝的 event 完成后才复用 buffer。

当前的 reader 配置：Wan 所有 stage 共用一个 24 reader 的池；H3 每个组件各有一个池（Qwen 和 DiT 各 24，video encoder 6，video decoder 8，audio VAE 和 audio encoder 各 4）；LTX 在 Modal 示例里共用一个 48 reader 的池。Chunk 都是 32 MiB。

3. 框架 API 实际管理什么

Rust DeclaredStartup 负责释放任务、解析依赖、执行 serial group 和计算前的 consumer gate。Wan 和 LTX 用 Rust 声明；H3 用 Python 声明，绑定到同一个执行器。

字段或方法含义需要注意的边界
Component.afterLoad 等待这些组件或静态 Preparation。H3 的 video decoder 和 audio VAE 在输入组件之后加载。
Component.required_preparations使用该组件的 consumer 在计算前需要的 Preparation。省略和空列表不同：空列表表示明确不需要。
Component.load_at_use只在 consumer 需要时才启动加载。用于 H3 的输出组件。
Component.prefetch / read_ahead可选的文件预读。预读结束不代表 GPU 权重已就绪。
Component.readers（ReaderBudget）Reader 数、chunk 大小、上传槽位和 host buffer 上限。超出上限的预算在准入时就被拒绝。
NativeLoadPlan LoadModeStaged（Wan）、Independent（LTX）或 IndependentAtUse（LTX 的 ABI）。Staged 保持 GPU 上的 stage 顺序；读取可以提前。
Preparation.before计算前需要这个结果的 consumer。它不会推迟该组件的加载。
Preparation.weightsCallback 等待这些组件完成。它表示整个 Component 完成，不是单独的字节拷贝完成信号。
Preparation.afterCallback 等待这些 Preparation 的结果。这会形成数据依赖。
Preparation.prepare / cpu输入就绪后立即运行的 CPU 部分。它不等待 weights 字段。
Preparation.at_useAlways：在 consumer 首次使用时运行。Wan 的 dit-model 和 LTX 的 install-* 用它。
Preparation.serial_group组内同一时刻只运行一个就绪任务。它不规定固定顺序。H3 Ref2VA 的参考 conditioning 用它。
validate结果验证通过后，才释放依赖它的工作。验证失败绝不会变成正常完成。
invoke / before_use / check_before_use同一个 Rust consumer gate。before_use 会等待；check_before_use 立即返回当前状态。

5. First DiT 之前的最后一步

Wan

dit-model 在 DiT 首次使用时（conditioning 之后）基于已加载的权重构建 DiT，并分配请求 scratch。Attention plan 之前已由 request-backend 恢复，这一步不会重新读 checkpoint。

H3

request-shape-layout 在 DiT owner 里准备请求张量、位置表、稀疏 attention router 状态、scratch 和 workspace；conditioning 汇合后，request-layout 完成剩下的部分。

LTX

install-dit 把已加载的 DiT 视图装进 LTX 自己的张量；第一个采样 forward 随后按请求的 token 数规划 block 程序。

6. 哪些东西能在容器之间复用

项目可以复用的部分新 owner 仍需做的事
Checkpoint 文件与 manifest留在 Volume 上。把需要的权重字节放进 GPU 内存。
已编译的 GPU 代码与 plan bundle启动前已打进镜像。加载 GPU 代码，恢复运行时 plan。
文件页存储缓存可能已经有。仍要填 buffer、拷贝到 GPU。
CUDA context 与库 handle属于一个存活的进程。创建自己的。
GPU 权重与 scratch常驻 owner 可以继续使用。分配 buffer 并填入内容。

快速读文件只能缩短一部分工作，不会省掉 CUDA 初始化、GPU 拷贝、请求 buffer 和 encoder 计算。

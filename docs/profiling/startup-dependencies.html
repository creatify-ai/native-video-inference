Cold start: work and dependencies

How Wan 2.1, MiniMax H3 and LTX 2.5 load during a cold start in the current code: the three kinds of work, the path of a weight from file to GPU, what the framework API controls, and each model's declared dependencies. The page describes declarations, not measured times; the startup profile has real container timelines.

Work typesWork listWeight pathFramework APIDependenciesBefore the first stepReused stateTermsSources

Model preparation

Prepares the native owner, its CUDA state, model objects and work buffers.

It makes the owner ready to run model operations.

Weight preparation

Reads the trained parameters and puts them in GPU memory.

It answers: where are the parameter bytes, and can computation use them yet?

Request preparation

Prepares the inputs, encoder results and layout of one request.

It answers: which inputs, conditioning and tensor shapes does this request need?

These are not three APIs. One declared callback can contain more than one kind of work. Wan's request-backend runs the CPU front end first and then restores attention plans once the context exists; each H3 component's native load creates its context, starts readers and uploads in one callback. The executor schedules callbacks, so work overlaps only where it is split into separate callbacks.

2. The weight path

CPU readers can start before CUDA exists. Host-to-device copies wait for the CUDA context and a filled buffer.

CPU memory

A reader can fill a buffer before CUDA exists; that buffer is not yet registered with CUDA.

Buffers come from a bounded pool. The checkpoint is never held in pinned memory as a whole.

GPU memory

Once CUDA is ready, filled buffers are registered and copied. Later reads overlap earlier copies.

A returned copy call does not mean the bytes have landed. The loader waits for each copy's event before it reuses the buffer.

Readers today: Wan, one pool of 24 for all stages; H3, its own pool per component (24 for Qwen and the DiT, 6 for the video encoder, 8 for the video decoder, 4 each for the audio VAE and encoder); LTX, one shared pool of 48 in the Modal example. Chunks are 32 MiB.

5. Right before the first DiT step

Wan

dit-model builds the DiT over its loaded weights and allocates request scratch when the DiT is first used, after conditioning. Attention plans were restored earlier by request-backend, so this step does not read the checkpoint again.

H3

request-shape-layout prepares the request's tensors, position tables, sparse-attention router state, scratch and workspaces in the DiT owner; request-layout completes it once conditioning is assembled.

LTX

install-dit adapts the loaded DiT views into LTX's own tensors; the first sampling forward then plans its block program at the request's token count.
